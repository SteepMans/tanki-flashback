# Браузерный клиент (эксперимент)

Попытка запустить тот же SWF-клиент в браузере через [Ruffle](https://ruffle.rs) — эмулятор Flash
на Rust/WASM. Без установки AIR-клиента.

```
webclient/
  index.html      страница-обёртка: конфиг Ruffle + загрузка Prelauncher.swf
  ruffle/         selfhosted-сборка Ruffle v0.5.0 (js + wasm)
```

Отдаётся ресурсным сервером по `/web` (роут в `src/server/resource.server.ts`) — тем же origin,
что и `Prelauncher.swf`, `Loader.swf`, `library.swf` и игровые ресурсы, поэтому CORS не нужен.

## Запуск

1. Игровой сервер: `npm run dev -- --no-build`
2. Мост WebSocket → TCP:

```bash
python -m websockify 1338 127.0.0.1:1337
```

3. Открыть `http://localhost:9999/web/`

## Почему нужен мост

Браузер не даёт открыть сырой TCP. Ruffle это обходит: при вызове `flash.net.Socket` он ищет
подходящий `socketProxy` и туннелирует поток в WebSocket. websockify на той стороне разворачивает
его обратно в TCP до `1337`. Байты не трогаются, поэтому формат кадра
(`int32 длина | int32 packetId | тело`) остаётся прежним и клиент патчить не нужно.

Конфиг в `index.html`:

```js
socketProxy: [{ host: "127.0.0.1", port: 1337, proxyUrl: "ws://<hostname>:1338" }]
```

## Что работает

Лобби, чат, список битв, гараж с 3D-превью танка и сам бой идут через Stage3D (аппаратный
рендерер клиента, `renderMode=direct`). Управление, выход из битвы и повторный вход проверяются
автотестами (см. ниже).

Изменения в Ruffle, без которых это не работало, лежат в `../../ruffle/` и `../../ruffle-patches/`.
Ключевые: отрисовка накапливается и уходит видеокарте одной посылкой за кадр (раньше — по посылке
на каждую модель, из-за чего в бою было 15–20 кадров в секунду), кешируются пайплайны и bind
group, слой Stage3D показывается через «окно», которое клиент вырезает в интерфейсе (превью в
гараже), и отключено многосэмпловое сглаживание бэкбуфера, не поддержанное в WebGL.

## Сборка клиента для браузера

`webclient/library.swf` — не оригинал, а сборка с патчами, которые нужны только в браузере
(в репозиторий не попадает, собирается на месте):

```bash
npm run patch:webclient
```

Патчи (`scripts/patches/`):

- `browser-nostorage` — выключает локальный кэш ресурсов: под Ruffle `SharedObject.flush()` бросает
  Error #2130 и обрывает догрузку (гараж оставался пустым).
- `browser-fps-slider` — поднимает потолок ползунка «Предельная частота кадров» с 60 до 120.
  В браузере клиент не умеет спрашивать частоту монитора и упирался в 60; этот же потолок
  обрезал показания встроенного счётчика FPS в правом нижнем углу.
- `browser-render-scale` — добавляет в настройки («Игра») флажок «Чёткая отрисовка (x2)»:
  множитель разрешения кадра. Значение хранит страница, клиент дёргает её через
  `ExternalInterface` (`window.ruffleRenderScale2x`).

В десктопную сборку (`npm run patch:client`, деплой в `.resource/`) эти три патча НЕ попадают:
десктопу они не нужны, а без кэша ресурсов он качал бы их заново каждый запуск.

## Настройки, влияющие на производительность

- «Игра» → «Чёткая отрисовка (x2)»: кадр рисуется вдвое подробнее экрана, браузер сжимает его
  обратно. Мелкий текст перестаёт мылиться (вшитых шрифтов в клиенте нет, движок рисует подписи
  запасным шрифтом без хинтинга) ценой нагрузки на видеокарту. По умолчанию включено,
  `?render=<число>` перебивает выбор.
- «Графика» → «Предельная частота кадров»: значение уходит в `stage.frameRate`, Ruffle его
  слушает. Выше 60 имеет смысл только на мониторе с частотой выше 60 Гц: кадры движок рисует по
  `requestAnimationFrame`. `?fps=<число>` задаёт частоту принудительно и на это время отключает
  ползунок.

`StandaloneLoader.swf` в браузере не используется: он AIR-only (`NativeApplication`, `NativeWindow`,
`StageWebView`, `Screen`). Страница грузит сразу `Prelauncher.swf`, локаль передаётся flashvar'ом.

## Автотесты

Требуются установленный Chrome, поднятый сервер и мост. Аккаунт для тестов создаётся командой
`npx tsx scripts/e2e-account.ts`.

```bash
node webclient/e2e.js --battle --shot   вход, гараж, бой, клавиши, выход из битвы, повторный вход
node webclient/e2e.js --battle --bonus  дополнительно сбрасывает припасы и катается по карте
node webclient/e2e.js --battle --profile печатает самые дорогие функции по сэмплам процессора
node webclient/garage.js                гараж отдельно, с покадровыми снимками превью
node webclient/crate.js                 ящик припасов крупным планом
node webclient/settings.js              окно настроек: флажок чёткой отрисовки и потолок кадров
node webclient/smoke.js                 быстрая проверка, что страница вообще поднялась
node webclient/soak.js --minutes 15     длинный бой с ботами: ищет, что копится со временем
node webclient/soak.js --rounds 5       пять заходов в бой подряд: копится ли что-то между боями
```

Снимки и логи (`*.png`, `e2e.log`, `garage.log`) в репозиторий не попадают.

## Диагностика

- Счётчик поверх игры: FPS, время ActionScript и отрисовки, число вызовов Stage3D и посылок
  видеокарте. Прячется по F8, отключается `?stats=0`.
- Флаги в консоли браузера (читаются раз в секунду):
  `window.ruffleTraceDraws = true` — разбор вызовов отрисовки и состав команд Stage3D за секунду;
  `window.ruffleTraceUploads = true` — заливки текстур со средним цветом;
  `window.ruffleDrawLimit = N` — рисовать не больше N вызовов за кадр (искать, что перекрывает);
  `window.ruffleNoCache = true` — выключить кеши пайплайнов и bind group.
- `soak.js` раз в несколько секунд снимает замеры движка, размер линейной памяти WASM (в ней живут
  все объекты игры, поэтому её рост — прямой признак того, что клиент копит объекты), число узлов
  страницы и, с `--methods`, число ВЫЗОВОВ каждого горячего метода в секунду. Растущие вызовы у
  метода означают растущую коллекцию, по которой он бегает. Результат — таблица по минутам,
  `soak-<tag>.csv` и `soak-<tag>-methods.json` рядом.
- Плашка внизу слева показывает стадию загрузки.
- Консоль браузера — ошибки Ruffle (`logLevel` задаётся параметром `?log=`).
- `webclient/websockify.log` — соединения моста.
- Лог игрового сервера — дошёл ли клиент до `New client connected`.
